# Memory

Notes for future Claude sessions in this repository. Kept at the user's standing request ("keep a memory file"). Durable facts and decisions only; update it when one of them changes.

## The user

- Works in Claude Code on the web (cloud sessions). The container is ephemeral, so anything worth keeping is committed and pushed.
- Standing preferences: keep a memory file; research before editing; prove claims with tool output rather than asserting them; finish the work instead of stopping to ask.
- 2026-11-20: asked for the graphify repo, a "Claude Code Behaviour Guidelines" prompt and two prompt screenshots (an overnight engineering crew; a Claude Code cost auditor) to be combined into one repeatable agentic coding team, as a skill or plugin. Plans to test it on a new project.

## What was built: `plugins/crew`

A Claude Code plugin named `crew` (marketplace `mkculp`, manifest at `.claude-plugin/marketplace.json`). See `plugins/crew/README.md` for use.

- `skills/crew/SKILL.md`: the Lead's playbook. Kept under 5,000 tokens so it survives context compaction whole; detail lives in `skills/crew/references/`.
- `agents/{mapper,breaker,builder,prover,reviewer}.md`: the five roles, with model and effort set in frontmatter.
- `skills/crew/scripts/crew.py`: the proof harness and state machine. Every gate is a tool run.
- `skills/crew/scripts/guard.py`: PreToolUse hook. Prevention only, fails open; `crew prove` is the authority.
- `skills/crew/scripts/audit.py`: cost audit, measured from session transcripts.
- `skills/crew/scripts/install.py`: copies the crew into a project's `.claude/` for cloud sessions.
- `tests/`: pytest, real temporary git repos. Run `uv run --frozen pytest plugins/crew/tests -q`.

Scripts live under the skill folder, not a top-level `scripts/` or `bin/`, so `${CLAUDE_SKILL_DIR}/scripts/...` resolves the same way in the plugin and in a project install (and claude.ai refuses plugins with a top-level `bin/`).

## Design decisions, and why

- The source prompts conflict on effort: the behaviour guidelines say always think at maximum depth, the cost auditor says make medium the default. Resolved by routing: high effort for Breaker and Reviewer, where understanding decides the outcome; small models for Mapper and Prover; Builder at medium, raised only after a second rejection.
- They also conflict on asking: "wait for my go" versus "do not seek permission". Resolved as one approval gate (the plan), after which the crew parks an issue with one question instead of asking.
- The proving test is sealed by blob hash, and its red run is done on the base plus the test files only. That is what makes "failed before, passes after" checkable instead of claimed.
- Proofs run in a throwaway `git worktree` of the head commit, so "green on a clean checkout" is literal.
- The crew makes its own worktrees under `.crew/wt/`. Claude Code's `isolation: worktree` branches from the default branch, so a builder would not see the Breaker's test.
- `crew` writes the brief, the PR body and TASKS.md from recorded evidence, so reports cannot claim more than was proven.

## Facts verified on 2026-11-20 (Claude Code 2.1.329)

- Cloud sessions do not load marketplace plugins or a repo's `enabledPlugins`. They do read the repo's `.claude/skills`, `.claude/agents` and the hooks in `.claude/settings.json`.
- Plugin agents ignore `hooks`, `mcpServers` and `permissionMode` in frontmatter; `model`, `effort`, `tools`, `disallowedTools`, `maxTurns` work.
- Hook input carries `agent_type` inside subagents (`crew:builder` for plugin agents) and none on the main thread.
- Session transcripts are at `~/.claude/projects/<slug>/<session>.jsonl`, subagents under `<session>/subagents/agent-*.jsonl` with a `.meta.json` holding `agentType`. Usage repeats once per content block, so count once per `requestId`.
- `claude plugin validate <path> --strict` validates the plugin and the marketplace.
- A nested `claude -p ... --plugin-dir plugins/crew --permission-mode acceptEdits --allowedTools ...` session runs in the cloud container and loads the real plugin. This is how the end-to-end trial was run; `--resume <session id>` continues it.

## Repository conventions that bite

- `.gitignore` ignores every `skills/` and `.claude/` directory. `plugins/crew/skills/` is re-included by an explicit rule; a new plugin needs its own.
- Skill files under `graphify/` are generated by `tools/skillgen`. Never hand-edit them; `uv run python -m tools.skillgen --check` must stay green.
- Cloud sessions clone this repository shallow. Eleven tests in `tests/test_skillgen.py` read an old baseline commit with `git show` and fail with "could not read 47042beb..." until you run `git fetch --unshallow origin v8`. On 2026-11-20 the full suite gave 11,645 passed and exactly those 11 failed in the shallow clone; after the fetch `tests/test_skillgen.py` passes (80 passed).
- `uv sync` without `--frozen` rewrites `uv.lock`. Use `--frozen`, or `git checkout -- uv.lock` afterwards.
- `uv run --frozen pyright` reports several hundred errors in upstream `graphify/` and `tests/` at v0.9.113. Pyright is not part of CI. `uv run pyright plugins/crew/skills` should stay clean.
- `AGENTS.md` says to use `graphify-out/` and run `graphify update .` after code changes. `graphify-out/` is gitignored and absent in a fresh clone; `graphify update .` rebuilds it in about 30 seconds with no model calls.
- "graphify" is a mark of Graphify Labs. Anything built here is community work: say so, and keep "graphify" out of plugin and marketplace names.
- Upstream is `Graphify-Labs/graphify`, active branch `v8`. This fork is `mkculp/graphify`. PRs follow `.github/PULL_REQUEST_TEMPLATE.md`; commits use conventional prefixes.
